Why description quality is a bug class

The description is an API surface, because the thing reading it is deciding whether to reuse or rebuild.

A vague entry does not produce a bad search result. It produces a false negative, and a false negative produces a duplicate that ships. Six entries are currently rated weak, and each one is a duplicate waiting to happen.

This is tested, not proofread. The check is whether a model, given only the registry, correctly answers "do we already do this?" including the cases where the answer is no.

ADR-010, in full

the one the whole system rests on
Question
Pull capabilities into a core, or leave applications heavy and run an auditor that finds drift?
Decision
Neither alone. Extraction decides where code lives; audit decides how you find out something should move. The rule: extract when a change to a capability must propagate, leave it and audit when a change must not.
Why not audit only
An auditor without a core produces proposals with nowhere to land, and cannot enforce a control. A control that depends on someone reading a weekly digest is not a control.
Why not extract everything
Two implementations that rhyme are not one capability. Forcing them together produces something that serves neither, and evaluation coverage caps how fast the core can safely grow anyway.
Reversal conditions
Fewer than four capabilities pass all criteria; or Anthropic ships a first-party registry that reads the existing format; or time from PRD to first working application increases after the first three extractions.
Working concept for discussion. Illustrative data throughout; this describes no running system.
